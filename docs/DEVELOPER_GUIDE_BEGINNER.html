Backbone State Tracker 초급 개발자 가이드

문서 버전: v0.8.57
작성일: 2026-06-15
대상: Python과 Windows 배포를 처음 유지보수하는 개발자

1. 프로젝트 목적

백본 3/4호기의 작업 전후 상태를 읽기 전용 명령으로 수집하고, 스냅샷 간 변경점을 GUI와 HTML/XLSX/JSON 리포트로 확인하는 Windows 운영 도구입니다.

2. 주요 파일

  • core/gui.py: Tkinter GUI, 화면 전환, 수집/비교 버튼 동작
  • core/diff_engine.py: 스냅샷 비교와 등급 분류
  • core/reporter.py: HTML, XLSX, JSON 리포트 생성
  • core/report_bundle.py: 공유 ZIP과 문서 이미지 포함
  • core/workflow.py: 기준 스냅샷과 사용자 지정 단계명 규칙
  • config/commands.yaml: 수집 대상 읽기 전용 명령 목록. v0.8.35부터 vrrp_status / show vrrp가 포함됩니다.
  • docs/images/: 사용자 가이드용 실제 화면 캡처

3. 개발 환경과 테스트

cd "<folder-that-contains-backbone_state_tracker>\backbone_state_tracker"
python -m pip install -r requirements.txt
$env:PYTHONPATH=(Split-Path (Get-Location) -Parent)
python -m unittest discover -s tests
python app.py --smoke-check

4. 현재 UI 구조

  • 첫 화면과 첫 메뉴는 장비 설정입니다.
  • 좌측 메뉴는 장비 설정, 비교 결과, 작업 로그입니다.
  • 상태 수집은 장비 설정 화면 안에 통합되어 있습니다.
  • 장비 설정 페이지는 세로 스크롤 가능한 Canvas 안에 구성해 장비 행이 늘어도 하단 수집 컨트롤에 접근할 수 있게 합니다.
  • 대상 장비는 기본 2개 입력 행을 만들고, 장비 추가로 필요한 만큼 행을 늘립니다.
  • 장비 YAML을 불러올 때 3대 이상이면 행을 자동 확장하고, 더 짧은 목록을 불러오면 남는 행은 빈 기본값으로 초기화합니다.
  • device_summary_var는 사용 N대 / 입력 N대 / 행 N개 형식으로 대상 장비 입력 상태를 표시합니다.
  • 사용자는 단계명만 입력하며, 비우면 점검시간_YYYYMMDD_HHMM으로 저장됩니다.
  • 수집/비교/샘플 검증 중에는 _track_busy_sensitive()에 등록된 실행 버튼을 비활성화합니다. 실행 흐름에 영향을 주는 버튼을 새로 만들면 같은 목록에 등록합니다.
  • 첫 수집은 기준 스냅샷, 이후 수집은 자동 비교 대상으로 처리됩니다.
  • v0.8.54부터 GUI 비교 결과에는 선택 변경 맥락 패널이 있으며, 선택 행의 등급/장비/명령/유형/라인을 항상 표시합니다.
  • HTML 리포트는 처음에는 등급 카드만 보이고, 사용자가 긴급/주의/정보/변경없음 중 하나를 선택해야 해당 상태의 바로가기 버튼, 요약 카드, 상세 블록이 표시됩니다. 숨김 상태는 [hidden] CSS와 aria-hidden 동기화로 보강합니다.
  • v0.8.54부터 HTML 리포트는 data-filter-state 안내 바, 상태별 톤이 있는 count card, 상세 블록 detail-head를 사용합니다.
  • 샘플 검증 스냅샷은 실제 작업 전 기준 후보에서 제외합니다.
  • GUI 상단 요약과 HTML 리포트 상단 메타에는 샘플 스냅샷을 샘플: 접두어로 표시합니다.

5. UI 디자인 기준

v0.8.52의 1단계 UI 현대화는 HPE Aruba AirWave 계열 운영 콘솔을 참고하되, 특정 제품 화면을 복제하지 않고 색감과 정보 계층만 반영합니다. v0.8.53은 같은 구조 안에서 주요 업무 화면의 안내 패널, 대상 요약, 선택 상태, 로그 가독성을 보강한 2단계 개선입니다. v0.8.54는 비교 결과와 HTML 리포트에서 필터 상태와 상세 맥락을 추적하기 쉽게 만든 3단계 개선입니다. v0.8.55는 이 기준을 문서, 화면 캡처, 릴리스 반입 체크리스트, ZIP 검증 흐름까지 맞춘 마감 단계입니다. v0.8.57은 현대화 전 문제 원인과 설계 대응을 명시해 후속 유지보수자가 같은 기준으로 판단할 수 있게 한 분석 보강 단계입니다.

현대화 전 문제 원인

  • 색상: 회색 기본 Tkinter 톤과 강조색 부재로 현재 메뉴, 주요 액션, 위험 상태가 한눈에 분리되지 않았습니다.
  • 여백과 테두리: 입력 폼, 표, 로그가 같은 무게로 붙어 보여 운영자가 반복 확인할 우선순위를 빠르게 잡기 어려웠습니다.
  • 버튼 우선순위: 실행 버튼과 보조 버튼의 시각 차이가 작아 주요 행동이 묻혔습니다.
  • 테이블과 비교 결과: 등급 카드, 행 단위 diff, 상세 값, 원본 열기 동선이 분산되어 변경 라인을 추적하기 어려웠습니다.
  • 로그: 일반 텍스트 영역처럼 보여 시간, 오류, 리포트 위치가 작업 증적처럼 읽히지 않았습니다.
  • 메뉴 배치: 장비 설정, 상태 수집, 로그, 비교가 분리되어 실제 운영 순서와 화면 이동이 어긋나는 느낌이 있었습니다.

설계 대응 요약

  • AirWave 계열의 어두운 내비게이션 레일과 Aruba teal 계열 강조색을 참고해 현재 위치와 주요 액션을 분리했습니다.
  • 장비 설정 안에 접속 계정, 대상 장비, 상태 수집을 모아 운영 순서와 화면 구조를 맞췄습니다.
  • _make_status_panel()과 compact chip으로 짧은 운영 문맥을 반복 사용하게 해 화면마다 같은 정보 계층을 유지했습니다.
  • SEVERITY_META와 HTML SEVERITY_COLORS/SEVERITY_SOFT_COLORS로 상태 색상을 일관화했습니다.
  • 비교 결과는 등급 필터, 행 단위 변경 표, 선택 변경 맥락, 상세 값 패널 순서로 읽히게 구성했습니다.
  • 작업 로그는 어두운 고정폭 표면으로 바꿔 운영 기록과 일반 폼 영역을 명확히 구분했습니다.
  • 공통 팔레트는 core/gui.py의 PALETTE를 기준으로 관리합니다.
  • 주요 액션은 Aruba teal 계열 accent를 사용하고, 보조 액션은 흰색/연한 회색 표면으로 둡니다.
  • 좌측 내비게이션은 어두운 운영 콘솔 레일로 두고, 현재 화면만 teal 배경으로 강조합니다.
  • 섹션은 얇은 테두리, 좌측 accent strip, 넉넉한 내부 여백을 사용합니다.
  • 업무 안내, 점검 상태, 실행 이력 같은 짧은 운영 문맥은 _make_status_panel()을 사용해 같은 높이, 좌측 stripe, soft 배경으로 표현합니다.
  • 등급 필터 카드는 선택 시 테두리만 바꾸지 말고 SEVERITY_META의 soft 배경까지 함께 적용해 현재 필터를 즉시 구분할 수 있게 합니다.
  • 장비 수, 실행 이력처럼 반복 확인하는 정보는 평문 라벨보다 compact chip 또는 어두운 로그 표면을 사용합니다.
  • 비교 테이블과 HTML 리포트는 같은 neutral surface, status color, compact card 원칙을 사용합니다.
  • 비교 상세처럼 사용자가 행을 선택해 추적하는 화면에는 선택 대상의 등급, 장비, 명령, 라인 위치를 별도 패널이나 헤더로 반복 표시합니다.
  • HTML 리포트의 인터랙션 상태는 DOM hidden과 aria-hidden을 함께 갱신해 화면 표시와 구조 테스트가 일치해야 합니다.
  • 새 색상이 필요하면 임의 색상보다 PALETTE에 의미 있는 토큰을 먼저 추가합니다.

컴포넌트 사용 기준

  • 새 업무 영역은 _make_section()으로 만들고, 안내/상태/실행 이력처럼 짧은 문맥은 _make_status_panel()을 사용합니다.
  • 장비 수, 현재 선택, 실행 상태처럼 반복 확인하는 값은 chip이나 status panel로 표현하고 긴 설명문으로 늘리지 않습니다.
  • 위험 등급을 표현할 때는 SEVERITY_META 또는 SEVERITY_COLORS를 거치고, 임의의 빨강/노랑/파랑 hex 값을 직접 쓰지 않습니다.
  • HTML 리포트 버튼/상세 블록은 GUI와 같은 Critical, Warning, Info, Unchanged 키를 기준으로 필터링해야 합니다.
  • 문서 스크린샷은 샘플 데이터와 TEST-NET 주소만 사용하고, 실제 계정, 실제 장비 IP, 원본 출력은 포함하지 않습니다.

6. 등급 분류 기준

등급기준
Critical장비 접속 실패, 명령 실패, 인터페이스 Down, LACP selected 수 감소, OSPF Full 이탈, cpu_usage 5초/1분/5분 70% 이상, memory_usage FreeRatio 30% 이하, power_status State 비정상, major alarm, fault, abnormal, offline, missing
Warningcpu_usage 5초/1분/5분 50~69%, memory_usage FreeRatio 31~40%, minor alarm, warning, error, 라우팅/STP/로그/리소스 변화
Infocpu_usage 5초/1분/5분 모두 50% 미만, memory_usage FreeRatio 40% 초과, 접속 복구 또는 일반 출력 변화
Unchanged정규화 후 의미 있는 변화가 없는 항목

cpu_usage와 memory_usage는 출력 변경량이 아니라 비교 대상 스냅샷의 현재 임계치 기준만으로 Critical, Warning, Info를 정합니다.

7. 릴리스 절차

  1. core/version.py의 APP_VERSION을 올립니다.
  2. CHANGELOG.md와 docs/VERSION_HISTORY.md/html을 갱신합니다.
  3. 사용자/명령어/개발자/체크리스트 문서를 MD와 HTML 모두 갱신합니다.
  4. 전체 테스트와 smoke-check를 실행합니다.
  5. GUI 변경 시 실제 앱 화면을 캡처해 검증합니다.
  6. 소스 ZIP과 Windows EXE ZIP을 빌드하고 Python/PowerShell 검증기를 모두 통과시킵니다.
